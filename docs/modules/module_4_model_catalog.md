# Kiro Project Documentation

## Module 4: Pattern Catalog and Constraints

### 1. Module Overview
*   **Name:** Pattern/Model Catalog and Constraints
*   **Main Objective:** Inventory clothing models (dresses, shirts, trousers, etc.) along with their technical cut constraints, serving as a reference base for the compatibility engine.
*   **Capabilities:** Create, view, modify, and remove a model profile; associate a model with compatible fabrics; define the body zones constrained by the model (chest, waist, hips).

### 2. System Positioning
*   **Module 3 - Fabric Catalog:** Provides the list of available fabrics to associate with models.
*   **Module 6 - Compatibility Engine:** Retrieves the constraints of the requested model from this module.
*   **Module 7 - Report:** Uses data from this module (the model's name and type appear in the final report).

### 3. Actors / Stakeholders
*   **User (End Client):** Submits an inspiration image of the desired garment to initiate the creation of a model.
*   **Recognition AI (Computer Vision):** Analyzes the submitted image to automatically deduce the garment type, cut type, and critical zones, generating a profile in "Draft" status.
*   **Administrator (Tailor/Expert):** Reviews and corrects the AI's deductions if necessary, associates compatible fabrics, and validates the publication of the model profile.
*   **Compatibility Verification Engine:** Consults a model's constraints to perform a verification.

### 4. Functional Description
This module allows for the creation of a comprehensive clothing model library. For each model, the cut type (fitted, semi-fitted, or loose), the constrained body parts, and compatible fabrics are specified. Once completed, this profile becomes the definitive reference consulted by the compatibility engine to judge if a garment suits a given user. 

To ensure the reliability of technical data, the creation of a profile follows a semi-automated process: an initial draft is generated by artificial intelligence based on the client's uploaded photo. It is then mandatorily reviewed and completed (especially regarding fabric compatibility) by an administrator before being published and made actionable.

**Expected Result:** A complete model profile, published and immediately usable by the calculation and verification modules.

### 5. Glossary
*   **Model/Pattern:** Garment style or pattern offered in the catalog (e.g., sheath dress, loose shirt).
*   **Cut/Fit:** Degree of closeness of the garment to the body: *fitted*, *semi-fitted*, or *loose (ample)*.
*   **Constraint:** Refers to the various cuts and critical zones imposed by the design.
*   **Critical Zone:** Body part on which the model imposes a measurement constraint (chest, waist, hips).
*   **Compatible Fabric:** Fabric deemed suitable for this specific model by the creator/administrator, selected from the fabric catalog.

### 6. Use Cases

#### 6.1 Adding a New Model
*   **Action / Goal:** Register and qualify a new model in the catalog based on client inspiration.
*   **Trigger:** The end client uploads a garment photo.
*   **Steps:**
    1. The user (client) uploads the image of the desired model.
    2. The AI analyzes the image and pre-fills the technical fields (garment type, cut type, relevant critical zones). The profile status is set to "Draft".
    3. The administrator is notified. They verify and manually adjust the AI-generated fields in case of errors.
    4. The administrator selects compatible fabrics from the fabric catalog (Module 3).
    5. The administrator saves and publishes the profile.
*   **Result:** The model profile changes to "Published" status; it is now available in the catalog and usable by the compatibility engine.

#### 6.2 Consultation by the Compatibility Engine
*   **Action / Goal:** Retrieve a model's constraints to verify its compatibility with a user.
*   **Trigger:** A user initiates a compatibility check for a given model.
*   **Steps:**
    1. Module 6 queries the catalog using the model ID.
    2. The module returns the cut, critical zones, and compatible fabrics.
*   **Result:** The data is transmitted to the compatibility engine to calculate the verdict.

### 7. Business Rules
*   **Initialization:** A model can only be initialized via the submission of an image by the user.
*   **Completeness:** Each model must have at least one defined critical zone before publication.
*   **Validation:** No model can transition from 'Draft' to 'Published' status without explicit validation from an administrator.
*   **Fabric Requirement:** A model cannot be published without at least one assigned compatible fabric.
*   **Modification Rights:** Only the user who proposed the model or an administrator can modify it.
*   **Immutability:** Modifying an already published model must not retroactively alter reports generated using older versions of that model.

### 8. Model Statuses
*   **Published:** Model is complete and available for use by the compatibility engine.
*   **Draft:** Profile is currently being created, pending administrator review, and is not visible to other modules.
*   **Archived:** Model has been removed from the active catalog and is kept solely for historical integrity of previously generated reports.

### 9. Interactions with Other Modules
*   **Modules 5 & 6:** Interfaces for ease margins (*marges d'aisance*) calculations and compatibility verification.

### 10. Error Handling
*   **Incomplete Profile (missing critical zone):** Publication is blocked, and a precise error message indicates the missing field.
*   **Referenced Fabric Removed (from Module 3):** An alert is displayed on the relevant model profile, prompting the administrator to replace the missing fabric.
*   **Module 6 Request for Non-Existent/Archived Model:** Returns an explicit error response ("Model Unavailable") rather than failing silently.
